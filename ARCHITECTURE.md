# Architecture

_High-level architecture of the site after the move to WebGPU. This describes the target structure and how the parts fit together; the step-by-step path to get there is in `PLAN.md`._

## 1. Principles

1. **Two layers of rendering.** WebGPU draws everything graphical, on a background canvas. Compose draws the interactive UI, on a transparent canvas on top.
2. **One clock.** The heartbeat is the single source of truth for time. Every animation, simulation and transition takes its time from it.
3. **The core knows no framework.** Time, buses and navigation are pure Kotlin. Compose and WebGPU are plugged in through adapters.
4. **Dependencies point inward.** Features depend on adapters and the core; the core depends on nothing.
5. **Describe, then render.** The core describes *what* should happen (a transition with effects on a layer); the adapters decide *how* it's drawn.
6. **Generated, type-safe platform access.** WebGPU is used through bindings generated by our own WebIDL compiler, from a committed and pinned spec.
7. **Degrade gracefully.** No WebGPU, a lost GPU device or reduced-motion settings all lead to a working site, not a blank page.

### 4.2 Module graph

```mermaid
flowchart LR
    subgraph BL["build-logic (included build)"]
        Compiler["webidl-compiler<br/>Gradle plugin"]
    end
    Core[":core<br/>wasmJs + jvm"]
    Math[":math<br/>wasmJs + jvm"]
    Gltf[":gltf<br/>wasmJs + jvm"]
    WebGpu[":webgpu<br/>wasmJs library"]
    App[":composeApp<br/>wasmJs executable"]
    IDL[("idl/webgpu.idl<br/>committed")]

    IDL --> Compiler
    Compiler -.->|"applied to, generates sources"| WebGpu
    Math --> Gltf
    Gltf --> App
    App --> Core
    App --> WebGpu
```

- **`build-logic/webidl-compiler`**: the WebIDL → Kotlin compiler, packaged as a Gradle plugin, with its own tests (fixtures, golden files, TestKit).
- **`:core`**: heartbeat, buses, navigation. The jvm target exists only so tests run fast without a browser.
- **`:math`**: the geometry the 3D pieces share: vectors, quaternions, 4×4 matrices laid out as WGSL's, boxes. Its own module because the camera needs it without glTF.
- **`:gltf`**: reads `.glb` models into a `Model` (vertex arrays, instances, materials, encoded images). It knows no GPU and no browser; the app uploads the arrays and the browser decodes the images.
- **`:webgpu`**: generated bindings and the hand-written idiomatic layer (`GpuContext`, resource scopes and staging typed arrays, shader diagnostics).
- **`:webidl-runtime`**: the small runtime every generated bindings module calls into: `createJsObject` for dictionaries, `await` that keeps the JS error. It knows no spec, so `:webgpu` and `:webaudio` share it without depending on each other.
- **`:webaudio`**: Web Audio bindings from the same compiler, for the rain.
- **`:design-system`** (`com.cdodi.design`): the look, DESIGN.md's "Autumn Rain". The theme as a value (colours by role, glass, scene, type and its bundled fonts), the viewport, and the components. Compose only, and nothing of the app's: what it needs from the app comes through its ports, `GlassSink` and `MotionClock`.
- **`:composeApp`**: the site. Adapters, app shell and features live here, organised by package (`adapters/compose`, `adapters/gpu`, `shell`, `features/life`, `features/boids`, …), so a feature could later move into its own module without changing its dependencies.

### 4.5 `:math` — `com.cdodi.math`

Single precision throughout, like the GPU, and every matrix in the layout WGSL reads, so it goes to a buffer as it is.

```
com.cdodi.math
├── Vec3      points and directions: + − × ÷, dot, cross (right-handed), length, normalized, component min/max
├── Quat      rotations, glTF's (x, y, z, w) order: product (right-hand first), rotate, axisAngle
├── Mat4      column-major (glTF's `matrix`, WGSL's mat4x4f): product, transformPoint/Direction, inverse, determinant,
│             trs (glTF's node order), perspective (WebGPU's 0–1 depth, looking down −Z), lookAt
└── Bounds    axis-aligned boxes: centre, size, radius, union, transformed (the box around the moved corners)

src/commonTest/            Mat4Test (layout, inverse of random transforms, the projection's depth) · QuatTest · BoundsTest
```

### 4.6 `:gltf` — `com.cdodi.gltf`

A reader, not a loader: `Gltf.read(bytes)` turns a `.glb` into a `Model`, and stops there. Uploading and decoding are the app's (`adapters/gpu/model`).

```
com.cdodi.gltf
├── Gltf          read(bytes) → Model · the extensions a file may require · GltfException (what, and where)
├── glb/          Glb: the container (header, JSON chunk, BIN chunk; other chunks skipped)
├── schema/       the JSON document as the spec names it (@Serializable, the spec's defaults; unknown keys skipped)
├── read/         Accessors (typed views → arrays; strides, normalized integers, everything bounds-checked first)
│                 SceneGraph (the scene's node trees → world matrices) · ModelReader (meshes, instances, materials)
└── Model         Mesh (primitives + where it's drawn: one matrix per node and per GPU instance) · Primitive (flat
                  position/normal/tangent/UV arrays, indices, bounds) · Material (metallic-roughness) · TextureRef ·
                  Sampler · Image (still encoded, with its MIME type)

src/commonTest/            GlbTest · AccessorsTest · GltfTest (.glb files built in memory by TestGlb)
src/jvmTest/               FixtureTest: real files from other exporters (resources/fixtures, credited in its README)
```

**The subset it reads, on purpose:** the `.glb` container with its images inside it, triangles, the core metallic-roughness material, and `EXT_mesh_gpu_instancing` (`KHR_mesh_quantization` too, since its integer attributes are read anyway). A file that *requires* any other extension is refused with the extensions named, rather than drawn wrong; extensions a file only *uses* (a clearcoat) are ignored. No animation, skins, morph targets, cameras, sparse accessors, or compressed meshes and textures: models are prepared offline into this subset.

**A mesh is stored once and drawn where it's used.** Nodes that share a mesh, and the instances of `EXT_mesh_gpu_instancing`, all become that mesh's instance matrices: the renderer draws it in one instanced call.

### 4.7 `:webgpu` — `com.cdodi.webgpu`

Generated code at the bottom, on the shared `:webidl-runtime`, and a hand-written idiomatic API that the app actually uses.

```
com.cdodi.webgpu
├── bindings/     GENERATED into build/generated — never edited by hand
│                 Enums.kt · Dictionaries.kt · Interfaces.kt · Namespaces.kt · Suspend.kt
├── context/      GpuContext · requestGpuContext() (null = no WebGPU) · hasFeature
│                 awaitLoss · onUncapturedError · errorScope { }
├── resource/     ResourceScope (creates and destroys raw GPUBuffer/GPUTexture objects)
│                 Float32Staging · Uint32Staging (reused typed arrays for uploads)
├── shader/       compileShader() (compile diagnostics with line/column) · loading .wgsl comes with the scenes
└── layout/       (later) UniformWriter · WGSL alignment helpers, see PLAN Phase 9
```

`composeApp` should only need `context`, `resource`, `shader`, `layout` and, inside scenes, `bindings`. The runtime (`:webidl-runtime`) is an implementation detail of the generated code; the app uses its `await` only for promises of its own (a `fetch`, a buffer mapping).

### 4.9 Package dependency rules

```mermaid
flowchart TB
    main["main.kt"] --> shell
    shell --> features
    shell --> adapters
    features --> adapters
    features --> ds[":design-system"]
    adapters --> ds
    adapters --> coreM["com.cdodi.core"]
    features --> coreM
    adapters --> gpuM["com.cdodi.webgpu"]
    features --> gpuM
    shell --> coreM
```

- `shell` → everything; nothing depends on `shell` except `main.kt`.
- `features.*` → `adapters`, `design`, `core`, `webgpu`. **Never** another feature, never `shell`.
- `adapters` → `design`, `core`, `webgpu`. Never `features` or `shell`.
- `design` (`:design-system`) → Compose only. No `core`, no GPU, no app state: the build enforces it.
- `core` → nothing in the project.
- `math` → nothing in the project; `gltf` → `math` (and kotlinx-serialization, for its JSON). Neither knows Compose, WebGPU or the DOM.

Colours have a rule of their own: they come from the theme. `checkThemeTokens` (a root task, over both modules and the shaders) fails on a colour written anywhere outside the design system's `theme` package: `Color(0x…)` or `Color(r, g, b)` in Kotlin, `vec3f(r, g, b) / 255` in a shader. The shaders read the theme's colours from one uniform buffer, `struct Theme` in `common/theme.wgsl`, which `GpuTheme` writes whenever the theme changes.

The design system is a module of its own, so the build keeps it from depending on the app: what it needs from the app comes through its ports, `GlassSink` (the GPU layer blurs the street behind the panes; `GpuWidgets` implements it) and `MotionClock` (UI motion on the heartbeat's `ui` clock, `Clock.asMotionClock()`), both provided by `main.kt`. Inside `:composeApp` the compiler can't enforce the other rules, so `checkPackageRules` does: it reads every import, and fails the build (and CI) when one crosses a rule, or when a top-level package other than `shell`, `features` and `adapters` appears. Once a rule needs bending often, that's the signal to move `features/*` (or `adapters`) into their own Gradle modules.

## 5. Runtime view

### 5.1 The two canvases

```
┌──────────────────────────── browser viewport ─────────────────────────────┐
│  <div id="compose">  z-index 1 — Compose canvas (Skia on WebGL2)          │
│     transparent except for widgets                                        │
│     ├─ widgets (menu, buttons, sliders, HUD)      ← take their input      │
│     └─ full-screen input Box                      ← everything else       │
│                                                                           │
│  <canvas id="gpu">   z-index 0 — WebGPU, pointer-events:none              │
│     SceneHost → active scene(s)                                           │
└───────────────────────────────────────────────────────────────────────────┘
```

Clicks never reach the WebGPU canvas directly. Compose's hit-testing sends them to a widget if one is under the pointer; otherwise the full-screen input Box receives them and hands them to the active scene. Both layers live in the same Wasm module, so this is a plain function call.

### 5.2 One frame

```mermaid
sequenceDiagram
    participant RAF as requestAnimationFrame
    participant CF as Compose frame clock
    participant HB as Heartbeat
    participant In as Input phase
    participant Sim as Simulation phase
    participant Nav as Navigation phase
    participant R as Render phase
    participant UI as UI phase
    participant GPU as GPU queue
    participant C as Compose draw

    RAF->>CF: frame(timestamp)
    CF->>HB: tick(nanos)
    HB->>In: apply pointer/keyboard input
    HB->>Sim: scenes step on their clocks
    HB->>Nav: advance transition progress
    HB->>R: SceneHost encodes passes (+ GPU effects)
    R->>GPU: queue.submit
    HB->>UI: publish Frame / state for Compose
    CF->>C: recompose + draw widgets (+ UI effects)
```

Everything in a frame sees the same `Frame` (index, timestamp, `dt`, `elapsed`), dispatched synchronously in a fixed phase order. That's what keeps the GPU scene, Compose animations and navigation transitions in step. Child clocks (`life`, `boids`, `transitions`) can be paused or slowed on their own; the global time scale affects all of them, and the lifecycle bus pauses the heartbeat when the tab is hidden.

### 5.3 Navigation

```mermaid
sequenceDiagram
    actor User
    participant W as Widget / browser back
    participant NB as NavigationBus
    participant N as Navigator (core)
    participant HB as Heartbeat (transitions clock)
    participant UIR as UI effect renderers
    participant GR as GPU effect renderers
    participant SH as SceneHost
    participant H as History adapter

    User->>W: click "Boids"
    W->>NB: NavigateTo(Boids)
    NB->>N: intent
    N->>N: pick the most specific edge → its Transition
    N->>SH: prepare Boids scene
    loop every frame
        HB->>N: advance
        N->>UIR: segment progress (Layer.Ui effects)
        N->>GR: segment progress (Layer.Gpu effects)
    end
    SH-->>N: signal sceneReady(Boids)
    N->>N: condition met → next segment → Idle(Boids)
    N->>NB: NavState
    NB->>H: push #/boids
```

A **transition** is a value built from basic transitions (one completion rule plus effects) with operators: `a + b` in sequence, `a with b` in parallel, `a or b` whichever finishes first. The navigator walks that tree on the transitions clock and hands each effect only *its own* segment's progress, so effects stay reusable no matter how they're combined.

## 6. Anatomy of a feature

Every page follows the same shape, so adding one means filling in the same slots:

```mermaid
flowchart LR
    D["Destination<br/>id + arguments (URL)"] --> F["Feature registration"]
    S["Scene<br/>prepare · resize · update · encode"] --> F
    U["Overlay UI<br/>Compose controls, HUD"] --> F
    W["WGSL shaders<br/>compose resources"] --> S
    R["CPU reference<br/>(optional oracle / fallback)"] -.-> S
    F --> Shell["App shell:<br/>nav graph + SceneHost + renderer"]
```

| Feature | Scene (GPU) | Overlay UI (Compose) | CPU reference |
|---|---|---|---|
| Background | Bokeh, rendered at reduced resolution | Quality toggle | — |
| Game of Life | Ping-pong state buffers, compute step, grid render | Play/pause, rule, speed, population | `LifeEngine` (oracle + fallback) |
| Boids | Particle buffers, spatial grid (count → scan → scatter), instanced draw | Weights, radius, count, profiling HUD | Small-N step check |
| Home / About | Background scene only | Menu, content | — |

## 7. Build-time pipeline

```mermaid
flowchart LR
    IDL[("webgpu.idl<br/>committed")] --> Lex["ANTLR lexer + parser<br/>(committed grammar)"]
    Lex --> AST["Symbol collection<br/>→ model"]
    AST --> P["Semantic passes<br/>partials → mixins → dictionaries →<br/>typedefs → unions → external types"]
    P --> Gen["KotlinPoet back end"]
    Gen --> Src["Generated sources<br/>enums · dictionaries · interfaces ·<br/>namespaces · suspend wrappers"]
    Src --> Kc["Kotlin/Wasm compile of :webgpu"]
    Manual["./gradlew :webgpu:updateWebIdl<br/>-PwebrefVersion=…<br/>(by hand only)"] -.->|"overwrites, then committed"| IDL
```

Each pass takes a model and returns a new one, so the pipeline is a chain of pure functions. Golden tests pin the generated output; a spec update therefore shows up as a readable diff in the golden files.

## 9. Cross-cutting concerns

- **Errors and fallback.** `requestContext()` returns `null` when WebGPU is missing or no adapter is found, so the app shell shows a fallback (a message, and the CPU Game of Life) instead of crashing. A lost device is recreated once, then the app falls back. Shader compile errors are reported with line and column. Promise rejections keep the original JS error.
- **Resource ownership.** GPU buffers and textures belong to a scene's resource scope and are destroyed when the scene is disposed; nothing depends on the garbage collector to free GPU memory.
- **Performance.** Bulk data stays on the GPU; the CPU uploads only uniforms and small edits, through reused staging arrays. Per-frame CPU work in heartbeat subscribers stays small, because they run synchronously. A profiling HUD (GPU timestamp queries when available) shows the cost per pass and per phase.
- **Accessibility and motion.** `prefers-reduced-motion` slows or freezes the heartbeat; hidden tabs pause it.
- **Testing by layer.**

  | Layer | How it's tested |
  |---|---|
  | WebIDL compiler | Fixture IDL files, golden outputs, TestKit compile test |
  | Core | JVM unit tests with a manual clock; property-based tests for the transition laws |
  | Geometry and glTF | JVM and browser unit tests (random transforms against their inverses; `.glb` files built in memory, broken ones included); real files from other exporters as JVM fixtures |
  | Platform access | Browser smoke test (adapter, compute round-trip) |
  | Features | Browser tests comparing GPU results against the CPU reference (Life patterns, scan, one Boids step) |

## 10. Key decisions

| Decision | Why | Trade-off accepted |
|---|---|---|
| WebGPU for all graphics, Compose only for UI | Compute shaders make large simulations possible; one graphics API | Effects applied *to* Compose content must stay in Skia |
| Two stacked canvases, input routed through Compose | Compose can't pass clicks through; one input system is simpler and consistent | Relies on a workaround for Skiko's white clear until SKIKO-949 is fixed |
| Heartbeat as the single clock, driven by Compose's frame clock | Everything in sync; pausing and slow motion in one place | Synchronous dispatch means a slow subscriber delays the frame |
| Framework-independent core with adapters | Navigation and time logic testable on the JVM; renderers replaceable | More interfaces than a Compose-only app would need |
| Transitions as a composable algebra | Reusable pieces, complex transitions built from simple ones | Overall progress is only exact for fully time-based transitions |
| Own WebIDL compiler instead of hand-written or third-party bindings | Learning, full control, and a showcase project in itself | The compiler has to be maintained and tested like a product |
| Committed IDL, updated only by hand | Reproducible, offline builds; spec changes are reviewed diffs | Updating the spec is a deliberate manual step |
| Our own glTF reader and renderer instead of an engine (Filament, three.js) | An engine brings its own canvas or device, loop and clock: the glass and the fog couldn't draw over its model in the same frame. And building it is the point | Only the subset we use is read; models are prepared offline into it |
| kotlinx.serialization for the glTF JSON | JetBrains' own, on every target; the schema becomes data classes with the spec's defaults. What glTF means is the interesting part, not reading JSON | A compiler plugin in the build |
