# Implementation Plan — Moving to WebGPU

_Written 2026-09-21, revised the same day with the owner's architecture decisions. Based on `REVIEW.md` (main review and the `cdodi/webgpu-test` branch review) and two research passes: Compose-for-Web layering, and Kotlin/Wasm interop and WebIDL. Versions are the latest as of writing._

## Goal

All graphics run on WebGPU: the animated background, Game of Life and, as the flagship, Boids driven by compute shaders. Compose Multiplatform stays as a transparent UI layer on top (buttons, sliders, menus, text). The WebGPU bindings are generated by our own ANTLR + KotlinPoet WebIDL compiler, built to be correct and tested. Learning and an impressive result matter more than taking the shortest path.

## Architecture decisions

1. **Two stacked canvases.** A WebGPU canvas in the background; the Compose canvas on top, transparent except for widgets.
2. **The heartbeat is the single source of truth for time.** Everything that animates takes its time from it: Compose animations, WebGPU scenes, simulations and navigation transitions. Anything that needs to stay in sync, stays in sync.
3. **The buses stay, as the backbone between layers.** At least the heartbeat and the navigation bus; the lifecycle bus feeds the heartbeat's pausing. Their *implementation* is fixed (synchronous dispatch, no coroutine launched per event), but the design stays.
4. **Navigation logic is decoupled from framework logic.** The navigation model is pure Kotlin with no Compose or WebGPU imports: a graph of **destinations (nodes)** and **transitions (edges)**. Each edge configures how the transition completes (after a duration, or when a condition is met) and which effects play (a simple animation, a shader, …). Framework adapters only render what the model describes.
5. **WebIDL inputs are committed.** `webgpu.idl` and the ANTLR grammar live in the repo, and every build reads them from there. Downloading a newer version is a separate task that only runs when invoked by hand, and the result is reviewed as a normal diff.

### Facts the design relies on (from research)

- `ComposeViewport(viewportContainerId = "compose")` mounts Compose into a given element. It clears that element's children, and the element needs a definite size.
- Skiko's WebGL context has alpha enabled, **but Skiko clears the canvas to white every frame** (skiko#949 / SKIKO-949, still open). Workaround: on the root composable, `drawBehind { drawRect(Color.Transparent, blendMode = BlendMode.Clear) }`, and every full-screen container must be transparent (no default `Surface` background).
- Compose captures all pointer events on its canvas, and there is no API to let clicks pass through to the canvas underneath. So input for the simulations goes through a full-screen `pointerInput` Box placed under the widgets; Compose's hit-testing already sends it only the events that no widget took.
- `HtmlElementView` (CMP 1.11+) places HTML elements *above* the Compose canvas, so it isn't usable as the background layer.
- WebGL and WebGPU can't share textures (only copying is possible). **Anything drawn *by* Compose stays in Skia**, including effects applied to Compose content such as the pixel-melt transition. That's why the navigation model sends each effect to a *layer* (UI or GPU).
- Compose frames are driven by `requestAnimationFrame`, and `withFrameNanos` callbacks run inside that callback, so the heartbeat can tick in the same frame as Compose's own animations.
- WebGPU is available in Chrome/Edge 113+, Safari 26+, and Firefox 141+ (Windows) / 145+ (macOS). Firefox on Linux and some Linux GPUs don't have it. `navigator.gpu` can be missing, **and `requestAdapter()` can resolve to `null`**, so both need a fallback.
- Kotlin/Wasm externals accept `Int`, `Double`, `Boolean` and `String` directly. `Long` crosses as a JS **BigInt**, so WebIDL `long long` must map to `Double`. A JS null returned where Kotlin declares a non-null object type throws an NPE; for a non-null primitive it silently becomes 0/false.
- kotlinx-coroutines 1.11's `Promise.await()` **throws away the original JS error object**, so we keep our own `await` that preserves it.
- Kotlin↔JS typed-array copies go element by element. Keep bulk data on the GPU and upload only uniforms and small edits.

| WebIDL | Kotlin/Wasm output |

| extended attributes | KDoc (`[EnforceRange]`: "throws TypeError when out of range") |

## Phase 2 — Core runtime: heartbeat, buses, navigation  _(L — pure Kotlin, can run alongside Phase 1)_

All of this lives in `:core` and has **no Compose or WebGPU imports**. The jvm target exists so these tests run in milliseconds, with no browser.

### 2.1 Heartbeat v2 — the single clock
The design stays; the implementation gets rebuilt so it works as the central source of truth.

```kotlin
data class Frame(
    val index: Long,          // frame counter, for "every N frames" logic and readback rotation
    val timeNanos: Long,      // raw timestamp from the frame clock
    val dt: Float,            // scaled, clamped delta in seconds
    val elapsed: Double,      // scaled total time; Double, so it never drifts and needs no modulo
)

enum class FramePhase { Input, Simulation, Navigation, Render, Ui }

interface Heartbeat {
    val frame: StateFlow<Frame>                        // for UI readers (e.g. collectAsState)
    fun subscribe(phase: FramePhase, listener: (Frame) -> Unit): Subscription   // synchronous, same frame, ordered
    fun clock(name: String): Clock                     // child clock with its own pause/scale
    var timeScale: Float                               // global slow motion; 0 = frozen
    var paused: Boolean
}
```

- [x] **Synchronous, ordered dispatch.** `tick(nanos)` calls subscribers phase by phase within the same frame, with **no `scope.launch` per frame** (fixes REVIEW 2.2). Everything in one frame sees the same `Frame`, which is what keeps things in sync. The phase order is fixed: input is applied, simulations step, navigation transitions advance, GPU passes are encoded, then UI state is published.
- [x] **Child clocks** (`clock("life")`, `clock("boids")`, `clock("transitions")`) derive from the heartbeat, each with its own pause and time scale. Pausing the Life simulation stops only its clock; the background and transitions keep their shared, synchronized time. The global `timeScale` scales every clock, so the whole site can go into slow motion (useful for debugging transitions, and a fun demo).
- [x] **Fixed-step helper**: `clock.fixedSteps(step = 1/60f) { … }`, the accumulator from the old `Manager`, reused by simulations that must be deterministic.
- [x] **Lifecycle bus → heartbeat**: when the tab goes to the background, the heartbeat pauses; `prefers-reduced-motion` sets a reduced time scale or holds a static frame.
- [x] **Precision**: shaders get `elapsed` folded by the clock into a per-shader period (`elapsed mod period` computed in Double), so an f32 in the shader never loses precision and there's no global jump (fixes REVIEW 2.4).
- [x] Tests with a `ManualFrameSource`: phase order, dt clamping, pause/scale of child clocks, fixed-step accumulation.

### 2.2 Buses
- [x] `NavigationBus`: intents in (`NavigateTo(destination)`, `Back`, `Forward`), state out (`StateFlow<NavState>`). Built on `trySend`/`tryEmit` (no per-event coroutine, fixes the `AppEventBus` issue).
- [x] `LifecycleBus`: `Foreground`/`Background` (visibility) and reduced-motion changes; the heartbeat subscribes to it.
- [x] Buses are interfaces in `:core`; their platform sources (`document.visibilityState`, `matchMedia`) are adapters in `composeApp`.

### 2.3 Navigation model (business logic)
The graph is **destinations (nodes)** connected by **edges**. An edge carries a **transition**: a first-class, reusable, **composable value** that says how it completes and which effects it plays. The model never knows how an effect is drawn.

#### Transitions are values with an algebra

```kotlin
// basic transitions: one completion rule + effects
val menuMorph = transition(after(1500.ms, FastOutSlowIn)) {
    play(AnimatedEffect("menu-morph", layer = Layer.Ui))
}
val meltUntilReady = transition(whenever(Signals.sceneReady(Boids), timeout = 3.s)) {
    play(ShaderEffect("pixel-melt", layer = Layer.Ui))
}
val gpuDissolve = transition(after(800.ms)) {
    play(ShaderEffect("dissolve", layer = Layer.Gpu))
}

// composition: the result is again a Transition
val intoBoids = menuMorph + meltUntilReady          // sequence: A, then B
val fancy     = (menuMorph with gpuDissolve) + meltUntilReady   // A and C together, then B
val guarded   = meltUntilReady or transition(after(5.s)) { play(fallbackFade) }   // whichever finishes first

val siteGraph = navGraph(start = Home) {
    destination(Home); destination(About); destination(Life); destination(Boids)

    edge(from = any, to = any, transition = transition(after(1.s)) { play(ShaderEffect("pixel-melt", Layer.Ui)) })
    edge(from = Home, to = anyOf(About, Life), transition = menuMorph)
    edge(from = any, to = Boids, transition = intoBoids, onInterrupt = Interrupt.Reverse)
}
```

- [x] **The `Transition` type** is a small tree: `Basic(completion, effects)` at the leaves, and `Sequence`, `Parallel` and `Race` nodes built by the operators:
  - `a + b` → **sequence**: `b` starts when `a` completes. (`+` reads as "followed by", like concatenating strings or lists.)
  - `a with b` → **parallel**: both run at once; it completes when both have completed.
  - `a or b` → **race**: it completes when the first one completes; the other is cancelled.
  - Modifiers that also return a `Transition`: `a.delayed(200.ms)`, `a.withTimeout(3.s)`, `a.reversed()`, `a.repeatUntil(condition)`.
- [x] **Algebraic laws, tested**: `+`, `with` and `or` are associative (`(a + b) + c == a + (b + c)`; the tree gets flattened when it's built, so both spell the same `Sequence(a, b, c)`). `with` and `or` are commutative. `Transition.None` is the identity (`a + None == a`). Property-based tests check the laws on randomly generated transition trees; this is what makes composing them safe.
- [x] **Each effect gets its own progress**: the renderer for the menu morph only ever sees *its* segment's 0→1, whether the transition runs alone or inside `intoBoids`. That's what makes transitions reusable: an effect doesn't need to know what it was combined with.
- [x] **Overall progress**: a composite made only of time-based parts has a known total duration (sequence = sum, parallel = max), so overall progress is exact. As soon as a condition-based part is involved, overall progress is "known per segment" and the navigator reports which segment is active. A condition-based segment reports "waiting" (so its effect can loop) until its signal fires. Everything runs on the heartbeat's `transitions` clock, so composites follow the global time scale and stay in sync with everything else.
- [x] **Interrupting a composite**: `Reverse` plays the segments that already ran backwards, in reverse order, from the current point. `Replace` cancels the remaining segments. `Queue` lets the composite finish.
- [x] **Completion rules** (the leaves): `after(duration, easing)` (time-based), `whenever(signal, timeout)` (condition-based), and `and`/`or` on rules *inside one* basic transition (e.g. `atLeast(600.ms) and whenever(ready)`). The difference from the transition operators: rule combinators decide when *one* basic transition ends; transition operators combine whole transitions, each with its own effects.
- [x] **Effects are descriptions, not code**: `AnimatedEffect(id, layer, params)` and `ShaderEffect(id, layer, uniforms)`. Each names a layer (`Ui`, `Gpu`, or both), because Compose content can only be transformed in Skia and scenes only in WebGPU. The set of effect types stays open (a sealed base plus user-defined subtypes), so new kinds of effect need no change to the model.
- [x] **Edge matching**: the most specific edge wins (exact beats `anyOf`, which beats `any`). Ties are a validation error.
- [x] **Navigator state machine**: `Idle(destination)` → `Transitioning(from, to, edge, progress)` → `Idle(to)`. It has a back/forward stack and optional guards on edges (`allowIf { … }`). **Interruptions** follow each edge's policy: `Queue`, `Replace` (jump to the new target), or `Reverse` (play backwards from the current progress).
- [x] **Destinations with arguments**: `data class LifeDestination(val rule: String = "B3/S23")`, serialized to a URL path so pages can be linked (see 3.4).
- [x] **Graph validation at startup**: every destination reachable, no ambiguous edges, and every effect id has a renderer registered for its layer (the adapters register themselves). A misconfigured graph fails immediately with a clear message, not halfway through a transition.
- [x] Tests with a manual clock: edge selection, time-based and condition-based completion, timeouts, composite transitions (the progress each segment sees, sequence/parallel/race completion, interrupting in the middle of a composite), each interruption policy, back/forward, validation errors. Plus the property-based tests for the transition laws.

**Done when:** the heartbeat and navigation model are fully covered by JVM tests, and the site runs on them with the current Compose-only rendering (no WebGPU needed yet).

> **Done.** 79 `:core` tests run on the JVM and in the browser, including property-based law tests (and a mutation check that they fail when the rules break). The site runs on the heartbeat, the buses and the navigator: the page transitions come from the model's effect progress, Life steps on its own clock, and shaders read the ambient clock. A headless-Chrome run (DevTools protocol, clicking by coordinates) went through Home → About → Boids → Life → Home and ran a glider. Where the implementation differs from the plan above:
> - **Names**: `clock(name)` is `Clock.child(name)`, which returns the existing child of that name. The fixed-step helper is a `FixedStepper` class rather than a `clock.fixedSteps { }` extension. The interruption policy is `Interrupt` (in `graph`, since edges carry it), and `sceneReady` is `Signal.sceneReady(route)`. Tests tick the heartbeat directly, so there's no `ManualFrameSource`.
> - **Destinations**: a `Route` is a kind of destination (URL path plus argument codec) and is itself the exact edge matcher; a destination without arguments is a `SingletonDestination`, its own route. `DestinationCodec` turns destinations into readable URLs (`life?rule=B36/S23`, percent-encoded UTF-8).
> - **Edge matching** is dominance, like overload resolution: an edge wins only if it's at least as specific at both ends as every other candidate. `Home → any` against `any → Boids` is an ambiguity, not a tie-break. A singleton's pair with itself is skipped, since it can never be navigated.
> - **Back/forward** use ordinary edge selection. The back stack records intents; the screen follows along edges. `edge(...).andBack()` adds the opposite edge with the transition reversed, which is how "back plays the edge backwards" is expressed.
> - **Held effects**: an effect whose segment has finished holds its end state until the whole transition ends (Web Animations' `fill: forwards`), so in `melt with fade` the page stays melted while the fade finishes. Effects a race cancels are dropped. `EffectState.travelled` gives each effect's progress in the direction of travel, so a cross-fade stays right when a transition is reversed.
> - **Reduced motion** follows DESIGN.md instead of a global time scale: `Clock.pauseWhile(lifecycle) { … }` freezes the ambient clock, and the graph's `reducedMotion` transition (a 400 ms fade) replaces every edge's. A hidden page pauses the heartbeat, and the first frame back adds no time.
> - **Bus timing**: in the Navigation phase the running transition advances first, then new intents apply, so a new transition shows its first frame at zero. Compose reads state through `collectEachFrame` (set in the Ui phase), which avoids the one-frame lag of collecting in a coroutine.
> - **Still self-timed**: the menu's placement and shape modifiers keep their own 1500 ms animation; the `menu-morph` edge only matches their timing until the navigation renderer drives them (3.3). Destinations already live in `features/*`; the pages move there in Phase 3.
> - **Testing note**: Compose resources open `CacheStorage`, which fails in headless Chrome ("Unexpected internal error"), and the deployed site fails the same way. Browser-driven UI checks need an in-memory `CacheStorage.prototype.open` stand-in.

**What you learn:** designing a framework-independent domain model, state machines, designing a small algebra (operators, identity, associativity) and checking its laws with property-based tests, a registry-based extension point, deterministic testing of time-driven code.

## Phase 6 — Boids with compute shaders (flagship)  _(L)_

Built in steps; each step ships on its own. The simulation steps on the `boids` clock.

### 6.1 Naive O(N²) version
- [x] Particle buffers `{ pos: vec2f, vel: vec2f }`, ping-ponged. The compute pass applies separation, alignment and cohesion within a perception radius. Integration uses a max speed and max force, and edges wrap.
- [x] Rendering: the vertex shader reads the storage buffer directly (**no vertex buffer**); each boid is a triangle rotated to its velocity, drawn instanced.
- [x] Start with N = 4,096 and confirm it looks right. Turn the old `Rule`/`Vec2` code into a small CPU reference that checks one simulation step for N = 64.

### 6.2 Spatial grid (so it scales)
Per frame, compute passes over a grid whose cell size equals the perception radius:
1. Clear the per-cell counters.
2. **Count**: `atomicAdd` each boid into its cell.
3. **Prefix sum** (exclusive scan) over the cell counts: a scan inside each workgroup, a pass over the block sums, then an add-back pass (Blelloch-style).
4. **Scatter**: write boids into a buffer sorted by cell (a counting sort).
5. **Neighbour search**: each boid only looks at the 3×3 surrounding cells of the sorted buffer.

- [ ] _(not yet measured; see the notes)_ Goal: **100k+ boids at 60 fps** on a mid-range laptop GPU; try for 1M.
- [x] Unit test for the scan against a CPU scan on random input (browser test).

### 6.3 Interaction and parameters
- [x] Compose sliders for the rule weights, perception radius, max speed and boid count; these write a uniform buffer.
- [x] Pointer: attract with the left button, repel with the right; the wheel sets the radius.
- [ ] _(partly: colour by heading)_ Extras: predators (a second species), obstacles (signed distance fields in the shader), trails (render into a texture that fades out), colour by speed or heading.

### 6.4 Profiling HUD
- [x] If `has("timestamp-query")` (the typed setlike from 1.3/1.4) is true, request the feature and measure every pass. A Compose overlay shows the milliseconds per pass, the boid count and the FPS (from the heartbeat). Seeing where GPU time goes is both a learning tool and a showpiece.

**What you learn:** parallel algorithms (scan, counting sort, spatial hashing), GPU profiling, designing a simulation around memory access.

> **6.1–6.4 done**, apart from the extras and a measurement on real hardware. Checked in headless Chrome:
> - 32,768 boids form streams like a murmuration, and 262,144 run as well.
> - Holding the left button draws the flock into a knot at the pointer.
> - The HUD times every pass, on both the Boids and Life pages.

> **Tests:**
> - The scan matches a CPU scan on random input across every block boundary, up to 262,144 values.

> How it's built, where the plan left it open:
> - **The CPU reference is the old `Rule`/`Vec2` sketch, finished**: `Separation`, `Alignment` and `Cohesion` are `Rule`s, and `Vec2` is still a value class over an `Offset`. `step.wgsl` follows it operation for operation, so the naive step agrees boid by boid.
> - **The count pass keeps `atomicAdd`'s old value** as each boid's rank in its cell, so the scatter is a plain write with no second atomic.
> - **Cells** are at least the perception radius wide, and at least 3 across, so the 3×3 never visits a cell twice.
> - **The grid step writes its output in cell order**, so neighbours stay close in memory for the next frame too.
> - **A neighbour cap** (48) keeps a dense knot from costing more than open sky; the tests lift it.
> - **The scan** is a two-level Blelloch scan in 512-value blocks, up to 262,144 values; the grid stays at or below 512×512 cells.
> - **The rendering** follows DESIGN.md's murmuration: dark birds against a lit fog bank, the birds heading towards the lamp catching its light, with 4× MSAA so the small triangles don't shimmer.
> - **The flock size** ranges from 1,024 to 262,144 on a log slider, default 32,768. A million would need bigger buffers and wasn't tried.
> - **The time step** is the frame's own `dt`, capped at 1/30 s, rather than fixed steps: one simulation step per frame, so nothing stutters at high refresh rates.

> - **A browser bug the compiler now prevents.** Kotlin/Wasm passes `undefined` for a defaulted external parameter. Around the 17,000th call, Chrome's optimised `setBindGroup` throws on `setBindGroup(index, group, undefined)`, though the same call made again at once goes through. The glass passes reached that count in seconds; the site would have reached it in a minute or two of transitions. The WebIDL compiler now emits a declaration per prefix of trailing optional arguments, so JavaScript calls carry only the arguments given.
> - **Locally on Windows**, `wasm-opt` (Binaryen 130) sometimes crashes optimising the production build (0xC0000005). It runs cleanly with `--debug`, which serialises its passes, so it's a timing-dependent Binaryen bug rather than our module. CI's Linux build is the reference.

## Phase 9 — Stretch goals (pick any)

- **WGSL struct → Kotlin layout generator**: parse the `struct` blocks of the `.wgsl` files (a second ANTLR grammar), compute offsets with WGSL alignment rules, and generate Kotlin writers for uniform and storage buffers. This rules out alignment bugs, the most common WebGPU bug, and reuses your compiler toolkit.
- **A visual debugger for the navigation graph**: render the graph (nodes, edges, active transition, progress) as an overlay, driven by the same model.
- **A small WGSL preprocessor** (`#include`, `#define` for workgroup sizes).
- **Make the compiler general**: generate bindings for a second spec (Web Audio or WebXR) to prove it works beyond WebGPU; publish it to the Gradle Plugin Portal.
- **Recorded replays**: save and load Life patterns (RLE format) and Boids parameter presets. The heartbeat's deterministic fixed steps make replays reproducible.
- **A 3D model on Home: a bonsai behind the Welcome glass** (idea from 2026-10-18, not researched yet). Load a textured model, such as a bonsai tree, and maybe let the visitor turn around it by dragging.
  - **The question.** Can our own WebGPU setup do this, or is an engine better (Google's Filament, for example)?
  - **First opinion: our own renderer, kept small.**
    - Use glTF (`.glb`), the web's model format: mesh, materials and textures in one file, laid out to go straight into GPU buffers.
    - What's needed:
      - a small glTF reader: accessors become vertex and index buffers;
      - textures: the browser decodes the images, `copyExternalImageToTexture` uploads them, and a pass generates mipmaps;
      - a little matrix maths, and a depth buffer;
      - a lighting shader;
      - an orbit camera driven by the existing pointer input, eased on the heartbeat so it feels heavy, not fast.
    - It would be a scene or a GPU-backed widget like the About sphere. The glass, the fog transitions and the heartbeat would all apply as they do now.
    - Size: a contained "L" phase, not an engine. Leave out skinning, animation, shadows and multiple-model scenes.
  - **Why not an engine?**
    - Filament (and three.js or Babylon) would bring its own canvas or device, its own render loop and clock, and several MB of wasm or JS.
    - It couldn't share our WebGPU device, so the glass blur and the fog couldn't draw over it in the same frame.
    - It would also go against the project's aim of building the pieces ourselves.
  - **Things to settle when we come back:**
    - **Style.** A photoreal tree could clash with the fog and lamp mood. Probably stylised: a dark silhouette, an amber rim light, fog around it.
    - **The asset.**
      - Licence: CC0 or CC-BY.
      - Size: aim for a couple of MB. Draco or meshopt compression would need a decoder.
      - Leaves: alpha-tested cards.
    - **Fit.** How it sits with the Welcome rhombus, and how it behaves on phones.
    - **A cheaper start.** Render the model offline into a turntable sprite sheet first?

## Risks to watch

| Risk | Mitigation |
|---|---|
| The Skiko white-clear workaround breaks after a CMP update | Isolated in `AppRoot`, and a test screenshot in the smoke test; watch SKIKO-949 |
| No WebGPU (Firefox on Linux, some GPUs, older Safari) | Typed null path, CPU fallback page, clear message; the navigation graph works the same without the GPU layer |
| GPU device lost (driver reset, tab in background) | `device.lost` watcher recreates the device and scenes once, then falls back |
| A heavy subscriber delays the whole frame (synchronous heartbeat) | Keep per-frame CPU work small (the GPU does the heavy work); the HUD shows time per phase so problems are visible |
| Navigation framework grows too general | Start from the site's real transitions; add combinators only when an edge needs them |
| Uniform layout and alignment bugs | Helpers written against WGSL rules now; the Phase 9 generator later |
| Element-by-element Kotlin↔JS copies | Keep data on the GPU; reuse staging typed arrays; upload only small regions |
| Dictionary `null` vs `undefined` | Factories never set absent keys; a golden test and a runtime test cover it |
| A spec update changes the generated API | The IDL is committed and updated only by hand; golden tests show the change as a diff |

## Suggested order

Phase 0 → **Phase 1 and Phase 2 in parallel** (they're independent: one is build tooling, the other pure Kotlin) → Phase 3 → Phase 5 (simpler compute first) → Phase 6 → Phase 4 → Phase 7 → Phase 8. Life comes before Boids because it teaches ping-pong buffers, atomics and readback, all of which Boids needs. The background shader port can happen whenever it's needed as a break from compute work.
