# Implementation Plan — Moving to WebGPU

_Written 2026-09-21, revised the same day with the owner's architecture decisions. Based on `REVIEW.md` (main review and the `cdodi/webgpu-test` branch review) and two research passes: Compose-for-Web layering, and Kotlin/Wasm interop and WebIDL. Versions are the latest as of writing._

## Goal

All graphics run on WebGPU: the animated background, Game of Life and, as the flagship, Boids driven by compute shaders. Compose Multiplatform stays as a transparent UI layer on top (buttons, sliders, menus, text). The WebGPU bindings are generated by our own ANTLR + KotlinPoet WebIDL compiler, built to be correct and tested. Learning and an impressive result matter more than taking the shortest path.

## Architecture decisions

1. **Two stacked canvases.** A WebGPU canvas in the background; the Compose canvas on top, transparent except for widgets.
2. **The heartbeat is the single source of truth for time.** Everything that animates takes its time from it: Compose animations, WebGPU scenes, simulations and navigation transitions. Anything that needs to stay in sync, stays in sync.
3. **The buses stay, as the backbone between layers.** At least the heartbeat and the navigation bus; the lifecycle bus feeds the heartbeat's pausing. Their *implementation* is fixed (synchronous dispatch, no coroutine launched per event), but the design stays.
4. **Navigation logic is decoupled from framework logic.** The navigation model is pure Kotlin with no Compose or WebGPU imports: a graph of **destinations (nodes)** and **transitions (edges)**. Each edge configures how the transition completes (after a duration, or when a condition is met) and which effects play (a simple animation, a shader, …). Framework adapters only render what the model describes.
5. **WebIDL inputs are committed.** `webgpu.idl` and the ANTLR grammar live in the repo, and every build reads them from there. Downloading a newer version is a separate task that only runs when invoked by hand, and the result is reviewed as a normal diff.

### Facts the design relies on (from research)

- `ComposeViewport(viewportContainerId = "compose")` mounts Compose into a given element. It clears that element's children, and the element needs a definite size.
- Skiko's WebGL context has alpha enabled, **but Skiko clears the canvas to white every frame** (skiko#949 / SKIKO-949, still open). Workaround: on the root composable, `drawBehind { drawRect(Color.Transparent, blendMode = BlendMode.Clear) }`, and every full-screen container must be transparent (no default `Surface` background).
- Compose captures all pointer events on its canvas, and there is no API to let clicks pass through to the canvas underneath. So input for the simulations goes through a full-screen `pointerInput` Box placed under the widgets; Compose's hit-testing already sends it only the events that no widget took.
- `HtmlElementView` (CMP 1.11+) places HTML elements *above* the Compose canvas, so it isn't usable as the background layer.
- WebGL and WebGPU can't share textures (only copying is possible). **Anything drawn *by* Compose stays in Skia**, including effects applied to Compose content such as the pixel-melt transition. That's why the navigation model sends each effect to a *layer* (UI or GPU).
- Compose frames are driven by `requestAnimationFrame`, and `withFrameNanos` callbacks run inside that callback, so the heartbeat can tick in the same frame as Compose's own animations.
- WebGPU is available in Chrome/Edge 113+, Safari 26+, and Firefox 141+ (Windows) / 145+ (macOS). Firefox on Linux and some Linux GPUs don't have it. `navigator.gpu` can be missing, **and `requestAdapter()` can resolve to `null`**, so both need a fallback.
- Kotlin/Wasm externals accept `Int`, `Double`, `Boolean` and `String` directly. `Long` crosses as a JS **BigInt**, so WebIDL `long long` must map to `Double`. A JS null returned where Kotlin declares a non-null object type throws an NPE; for a non-null primitive it silently becomes 0/false.
- kotlinx-coroutines 1.11's `Promise.await()` **throws away the original JS error object**, so we keep our own `await` that preserves it.
- Kotlin↔JS typed-array copies go element by element. Keep bulk data on the GPU and upload only uniforms and small edits.

## Phase 1 — WebIDL compiler v2  _(L — the core of the project)_

Treat it as a real compiler: **front end** (ANTLR parse tree → AST), **middle end** (semantic passes over an immutable model), **back end** (KotlinPoet emission). Write the tests first; every bug from REVIEW W1 becomes a fixture before it gets fixed.

### 1.1 Structure and committed inputs
- [ ] Move `plugins/` to `build-logic/webidl-compiler`. Create the `webgpu` library module and apply the plugin there, so `composeApp` only depends on `:webgpu`.
- [ ] Extension DSL instead of hard-coded names:
  ```kotlin
  webIdl {
      idlFiles.from("idl/webgpu.idl")          // committed file, read on every build
      packageName = "com.cdodi.webgpu.bindings"
      externalTypes.put("EventTarget", "org.w3c.dom.events.EventTarget")
      // …
  }
  ```
- [ ] **Committed inputs, updated by hand:**
  - `webgpu/idl/webgpu.idl` is committed. `transpileWebIdl` declares it as an `@InputFile` and never touches the network.
  - `build-logic/webidl-compiler/src/main/antlr/WebIDL.g4` is committed, and the automatic grammar download is removed.
  - A task **only run by hand**, `./gradlew :webgpu:updateWebIdl -PwebrefVersion=3.84.0`, downloads `https://cdn.jsdelivr.net/npm/@webref/idl@<version>/webgpu.idl` (webref releases curated, parse-checked IDL roughly weekly) and overwrites the committed file. No other task depends on it, it isn't cacheable, and it prints a summary of what changed. The result is committed like any other change, and golden-test failures show exactly how the generated API moved. The IDL's first line records the version it came from.
  - The same kind of by-hand task for the grammar (`updateWebIdlGrammar -PgrammarRef=<commit>`), pinned to a grammars-v4 commit.
- [ ] Generate the ANTLR parser into a real package (`-package com.cdodi.webidl.parser`).
- [ ] Fix the `antlr` typo; remove the duplicated tasks and properties.

### 1.2 Test harness (before any fixes)
- [ ] **Mini-IDL fixtures**, one per construct: interface, inheritance, mixin + includes, partials, dictionary (required / optional / default / inheritance), enum, typedef, union (all objects / mixed / sequence + dictionary), sequence, FrozenArray, record, Promise, optional arguments with and without defaults, `undefined` return, `readonly setlike`, namespace constants, extended attributes, external DOM types.
- [ ] **Golden tests**: compare the generated `.kt` with committed expected files. Add an `-PupdateGoldens` flag.
- [ ] **Compile test**: a Gradle TestKit fixture project that applies the plugin to a wasmJs project and runs `compileKotlinWasmJs`. This proves the output actually compiles.
- [ ] **Runtime smoke test**: `wasmJsBrowserTest` that requests an adapter and runs the doubling compute shader. Skip it gracefully where WebGPU is missing.

### 1.3 Middle end: correct semantics
- [ ] Rewrite the resolution passes as **pure functions from one model to the next** (no mutating a map while iterating it; fixes REVIEW W1 "maps mutated while iterated"): `mergePartials → applyMixins → flattenDictionaries → resolveTypedefs → normalizeUnions → attachExternalTypes`.
- [ ] Record `optional` as its own flag, separate from having a default value.
- [ ] Carry nullability faithfully for every kind of type (objects, primitives, promises, sequences).
- [ ] Parse `readonly setlike<T>` and extended attributes (`[EnforceRange]`, `[Clamp]`, `[SameObject]`, `[SecureContext]`, `[Exposed]`) into the model.
- [ ] Types from outside this IDL (`EventTarget`, `Event`, `DOMException`, `ArrayBuffer`, `BufferSource`, `ImageBitmap`, `HTMLCanvasElement`, `EventHandler`…) are resolved through the `externalTypes` table. This finally uses the `EXTERNAL_TYPE` slice. An unknown type fails the build with a clear message instead of silently becoming `JsAny`.

### 1.4 Back end: type mapping

| WebIDL | Kotlin/Wasm output |
|---|---|
| `byte`, `octet`, `short`, `unsigned short`, `long` | `Int` |
| `unsigned long` | `Int` (KDoc notes the range; flag constants stay `Int`) |
| `long long`, `unsigned long long` | **`Double`** (JS Number, max 2^53−1; never `Long`, which is a BigInt) |
| `float` / `double` (unrestricted too) | `Float` / `Double` |
| `boolean`, `DOMString`/`USVString` | `Boolean`, `String` |
| `T?` | `T?`, for every kind of type |
| `undefined` return | `Unit` |
| `Promise<T>` | `Promise<JsType>` (primitives boxed: `JsNumber`, `JsString`; `Promise<undefined>` → `Promise<JsAny?>`) |
| `sequence<T>` / `FrozenArray<T>` | `JsArray<T>` (boxed primitives) |
| `record<K, V>` | small generated wrapper with `get`/`set`, or `JsAny` for now |
| optional argument (with or without default) | `= definedExternally` |
| interface | `external interface` (`external class` when it has a constructor), extending mapped DOM types |
| mixin + includes | members copied in; `Navigator includes NavigatorGPU` → extension property `Navigator.gpu` |
| dictionary | `external interface : JsAny` + factory function that **leaves unset keys out** (WebIDL only skips `undefined`, and `null` for an enum member is a TypeError) |
| enum | `sealed external interface` + companion object with camelCase `inline val`s (`GPUPrimitiveTopology.triangleList`), the same pattern kotlinx-browser uses |
| union as an argument | **one overload per flattened member**, like web-sys and kotlinx-browser. `GPUColor` → `(GPUColorDict)` and `(DoubleArray)` overloads |
| union as a property or return | marker interface if every member is an object, otherwise `JsAny` |
| `readonly setlike<DOMString>` | `val size: Int`, `fun has(value: String): Boolean`, `forEach`, `values()` |
| namespace + `const` | Kotlin `object` with `const val` |
| Promise-returning operation | extension `suspend fun …Suspend()` wrapper; overload without the trailing optional arguments |
| extended attributes | KDoc (`[EnforceRange]`: "throws TypeError when out of range") |

- [ ] Put the IDL member's name and spec link in KDoc, so the generated API documents itself.
- [ ] Split the output into files by kind (`Enums.kt`, `Dictionaries.kt`, `Interfaces.kt`, `Namespaces.kt`, `Suspend.kt`) so diffs stay readable.

### 1.5 Runtime (`:webgpu`)
- [ ] `await()` that **keeps the JS rejection reason**: `class JsPromiseRejection(val reason: JsAny?) : Exception(…)`. For `GPUError` / `DOMException`, surface `name` and `message`.
- [ ] `jsObject { }` builder that only sets present keys; `toJsArray` removed (it's in the stdlib).
- [ ] Buffer helpers: reusable `Float32Array` / `Uint32Array` staging buffers filled in place (never a fresh conversion per frame).

### 1.6 Idiomatic layer (hand-written on top of the generated code)
- [ ] `suspend fun Gpu.requestContext(): GpuContext?`. `null` covers both a missing `navigator.gpu` and a null adapter, and it can never NPE.
- [ ] `GpuContext`: device, queue, preferred format, a set of enabled features (through the typed `has()`), `device.lost` watcher, `uncapturederror` listener (possible once `EventTarget` is mapped), and `pushErrorScope`/`popErrorScope` helpers.
- [ ] Resource ownership: `GpuBuffer` / `GpuTexture` wrappers that are `AutoCloseable` (`destroy()`), plus a `ResourceScope` so a scene frees everything on dispose.
- [ ] Shader modules: after `createShaderModule`, check `getCompilationInfo()` and log errors with line and column.

**Done when:** all goldens, compile and smoke tests are green. The triangle and doubling demos compile with **zero `toJsNumber()` calls** and no nullability workarounds. `requestAdapter` returning null is handled at the type level. A normal build makes no network requests.

**What you learn:** compiler structure, the WebIDL spec in depth, Kotlin/Wasm interop rules, how web-sys / kotlinx-browser solve the same problems, testing code generators.

## Phase 2 — Core runtime: heartbeat, buses, navigation  _(L — pure Kotlin, can run alongside Phase 1)_

All of this lives in `:core` and has **no Compose or WebGPU imports**. The jvm target exists so these tests run in milliseconds, with no browser.

### 2.1 Heartbeat v2 — the single clock
The design stays; the implementation gets rebuilt so it works as the central source of truth.

```kotlin
data class Frame(
    val index: Long,          // frame counter, for "every N frames" logic and readback rotation
    val timeNanos: Long,      // raw timestamp from the frame clock
    val dt: Float,            // scaled, clamped delta in seconds
    val elapsed: Double,      // scaled total time; Double, so it never drifts and needs no modulo
)

enum class FramePhase { Input, Simulation, Navigation, Render, Ui }

interface Heartbeat {
    val frame: StateFlow<Frame>                        // for UI readers (e.g. collectAsState)
    fun subscribe(phase: FramePhase, listener: (Frame) -> Unit): Subscription   // synchronous, same frame, ordered
    fun clock(name: String): Clock                     // child clock with its own pause/scale
    var timeScale: Float                               // global slow motion; 0 = frozen
    var paused: Boolean
}
```

- [ ] **Synchronous, ordered dispatch.** `tick(nanos)` calls subscribers phase by phase within the same frame, with **no `scope.launch` per frame** (fixes REVIEW 2.2). Everything in one frame sees the same `Frame`, which is what keeps things in sync. The phase order is fixed: input is applied, simulations step, navigation transitions advance, GPU passes are encoded, then UI state is published.
- [ ] **Child clocks** (`clock("life")`, `clock("boids")`, `clock("transitions")`) derive from the heartbeat, each with its own pause and time scale. Pausing the Life simulation stops only its clock; the background and transitions keep their shared, synchronized time. The global `timeScale` scales every clock, so the whole site can go into slow motion (useful for debugging transitions, and a fun demo).
- [ ] **Fixed-step helper**: `clock.fixedSteps(step = 1/60f) { … }`, the accumulator from the old `Manager`, reused by simulations that must be deterministic.
- [ ] **Lifecycle bus → heartbeat**: when the tab goes to the background, the heartbeat pauses; `prefers-reduced-motion` sets a reduced time scale or holds a static frame.
- [ ] **Precision**: shaders get `elapsed` folded by the clock into a per-shader period (`elapsed mod period` computed in Double), so an f32 in the shader never loses precision and there's no global jump (fixes REVIEW 2.4).
- [ ] Tests with a `ManualFrameSource`: phase order, dt clamping, pause/scale of child clocks, fixed-step accumulation.

### 2.2 Buses
- [ ] `NavigationBus`: intents in (`NavigateTo(destination)`, `Back`, `Forward`), state out (`StateFlow<NavState>`). Built on `trySend`/`tryEmit` (no per-event coroutine, fixes the `AppEventBus` issue).
- [ ] `LifecycleBus`: `Foreground`/`Background` (visibility) and reduced-motion changes; the heartbeat subscribes to it.
- [ ] Buses are interfaces in `:core`; their platform sources (`document.visibilityState`, `matchMedia`) are adapters in `composeApp`.

### 2.3 Navigation model (business logic)
The graph is **destinations (nodes)** connected by **edges**. An edge carries a **transition**: a first-class, reusable, **composable value** that says how it completes and which effects it plays. The model never knows how an effect is drawn.

#### Transitions are values with an algebra

```kotlin
// basic transitions: one completion rule + effects
val menuMorph = transition(after(1500.ms, FastOutSlowIn)) {
    play(AnimatedEffect("menu-morph", layer = Layer.Ui))
}
val meltUntilReady = transition(whenever(Signals.sceneReady(Boids), timeout = 3.s)) {
    play(ShaderEffect("pixel-melt", layer = Layer.Ui))
}
val gpuDissolve = transition(after(800.ms)) {
    play(ShaderEffect("dissolve", layer = Layer.Gpu))
}

// composition: the result is again a Transition
val intoBoids = menuMorph + meltUntilReady          // sequence: A, then B
val fancy     = (menuMorph with gpuDissolve) + meltUntilReady   // A and C together, then B
val guarded   = meltUntilReady or transition(after(5.s)) { play(fallbackFade) }   // whichever finishes first

val siteGraph = navGraph(start = Home) {
    destination(Home); destination(About); destination(Life); destination(Boids)

    edge(from = any, to = any, transition = transition(after(1.s)) { play(ShaderEffect("pixel-melt", Layer.Ui)) })
    edge(from = Home, to = anyOf(About, Life), transition = menuMorph)
    edge(from = any, to = Boids, transition = intoBoids, onInterrupt = Interrupt.Reverse)
}
```

- [ ] **The `Transition` type** is a small tree: `Basic(completion, effects)` at the leaves, and `Sequence`, `Parallel` and `Race` nodes built by the operators:
  - `a + b` → **sequence**: `b` starts when `a` completes. (`+` reads as "followed by", like concatenating strings or lists.)
  - `a with b` → **parallel**: both run at once; it completes when both have completed.
  - `a or b` → **race**: it completes when the first one completes; the other is cancelled.
  - Modifiers that also return a `Transition`: `a.delayed(200.ms)`, `a.withTimeout(3.s)`, `a.reversed()`, `a.repeatUntil(condition)`.
- [ ] **Algebraic laws, tested**: `+`, `with` and `or` are associative (`(a + b) + c == a + (b + c)`; the tree gets flattened when it's built, so both spell the same `Sequence(a, b, c)`). `with` and `or` are commutative. `Transition.None` is the identity (`a + None == a`). Property-based tests check the laws on randomly generated transition trees; this is what makes composing them safe.
- [ ] **Each effect gets its own progress**: the renderer for the menu morph only ever sees *its* segment's 0→1, whether the transition runs alone or inside `intoBoids`. That's what makes transitions reusable: an effect doesn't need to know what it was combined with.
- [ ] **Overall progress**: a composite made only of time-based parts has a known total duration (sequence = sum, parallel = max), so overall progress is exact. As soon as a condition-based part is involved, overall progress is "known per segment" and the navigator reports which segment is active. A condition-based segment reports "waiting" (so its effect can loop) until its signal fires. Everything runs on the heartbeat's `transitions` clock, so composites follow the global time scale and stay in sync with everything else.
- [ ] **Interrupting a composite**: `Reverse` plays the segments that already ran backwards, in reverse order, from the current point. `Replace` cancels the remaining segments. `Queue` lets the composite finish.
- [ ] **Completion rules** (the leaves): `after(duration, easing)` (time-based), `whenever(signal, timeout)` (condition-based), and `and`/`or` on rules *inside one* basic transition (e.g. `atLeast(600.ms) and whenever(ready)`). The difference from the transition operators: rule combinators decide when *one* basic transition ends; transition operators combine whole transitions, each with its own effects.
- [ ] **Effects are descriptions, not code**: `AnimatedEffect(id, layer, params)` and `ShaderEffect(id, layer, uniforms)`. Each names a layer (`Ui`, `Gpu`, or both), because Compose content can only be transformed in Skia and scenes only in WebGPU. The set of effect types stays open (a sealed base plus user-defined subtypes), so new kinds of effect need no change to the model.
- [ ] **Edge matching**: the most specific edge wins (exact beats `anyOf`, which beats `any`). Ties are a validation error.
- [ ] **Navigator state machine**: `Idle(destination)` → `Transitioning(from, to, edge, progress)` → `Idle(to)`. It has a back/forward stack and optional guards on edges (`allowIf { … }`). **Interruptions** follow each edge's policy: `Queue`, `Replace` (jump to the new target), or `Reverse` (play backwards from the current progress).
- [ ] **Destinations with arguments**: `data class LifeDestination(val rule: String = "B3/S23")`, serialized to a URL path so pages can be linked (see 3.4).
- [ ] **Graph validation at startup**: every destination reachable, no ambiguous edges, and every effect id has a renderer registered for its layer (the adapters register themselves). A misconfigured graph fails immediately with a clear message, not halfway through a transition.
- [ ] Tests with a manual clock: edge selection, time-based and condition-based completion, timeouts, composite transitions (the progress each segment sees, sequence/parallel/race completion, interrupting in the middle of a composite), each interruption policy, back/forward, validation errors. Plus the property-based tests for the transition laws.

**Done when:** the heartbeat and navigation model are fully covered by JVM tests, and the site runs on them with the current Compose-only rendering (no WebGPU needed yet).

**What you learn:** designing a framework-independent domain model, state machines, designing a small algebra (operators, identity, associativity) and checking its laws with property-based tests, a registry-based extension point, deterministic testing of time-driven code.

## Phase 3 — Two-layer host and framework adapters  _(M)_

### 3.1 Page and layers
- [ ] `index.html`: `<canvas id="gpu">` and `<div id="compose">`, both `position:fixed; inset:0`. The GPU canvas gets `pointer-events:none; z-index:0`, the Compose div `z-index:1`. Body background dark. Add an inline loading indicator that disappears once Compose starts (REVIEW §6).
- [ ] `ComposeViewport("compose")`, with the transparency workaround in one place: an `AppRoot` composable that applies the `BlendMode.Clear` `drawBehind`. Remove the default `Surface` background. Keep a note to track SKIKO-949.
- [ ] Canvas sizing: CSS size × `devicePixelRatio`, updated on resize or DPR change. `context.configure(device, format, alphaMode = opaque)`.

### 3.2 Heartbeat driver (Compose adapter)
- [ ] One `LaunchedEffect` at the root: `withFrameNanos { heartbeat.tick(it) }`. Compose's frame clock is the *driver*; the heartbeat is the *source of truth* that every layer reads.
- [ ] Bridge Compose's built-in animations to the heartbeat's time scale by giving the root a `MotionDurationScale`, so global slow motion also affects Compose `animate*` calls. (Compose can scale time this way but not pause it; animations that must pause read the heartbeat directly.)

### 3.3 Navigation adapters
- [ ] **Compose navigation renderer**: observes `NavState` and renders the current destination, or both destinations during a transition. `AnimatedEffect`s on `Layer.Ui` are driven by **seeking a `SeekableTransitionState`** to the model's progress, so Compose transitions follow the model's timing exactly instead of running their own clocks.
- [ ] **UI shader effects**: an effect registry that maps ids such as `"pixel-melt"` to SkSL `RenderEffect` implementations, with the progress fed as a uniform. This is where the existing melt shader goes.
- [ ] **GPU effects**: `SceneHost` registers renderers for `ShaderEffect`s on `Layer.Gpu` (dissolve, cross-fade). They render both scenes to textures and blend them using the model's progress.
- [ ] **Signals**: `SceneHost` publishes `sceneReady(destination)` once pipelines are compiled and buffers allocated; condition-based edges wait on it.
- [ ] The morphing menu becomes an `AnimatedEffect` (`"menu-morph"`) instead of logic built into `main.kt`.

### 3.4 Browser history
- [ ] A `BrowserHistoryAdapter` keeps `NavState` in step with `window.history` and the URL (e.g. `#/boids`, `#/life?rule=B36/S23`). The browser back button plays the configured edge backwards, and every page, including parameters, can be shared as a link.

### 3.5 Scenes, input and fallback
- [ ] `Scene` contract and `SceneHost`:
  ```kotlin
  interface Scene : AutoCloseable {
      suspend fun prepare(ctx: GpuContext)            // compile pipelines, allocate buffers → then signal ready
      fun resize(width: Int, height: Int)
      fun update(frame: Frame, input: InputState)     // subscribed to the Simulation phase
      fun encode(encoder: GPUCommandEncoder, target: GPUTextureView)   // Render phase
  }
  ```
- [ ] **Input routing**: a full-screen background `Box(Modifier.pointerInput { … })` under the widgets turns pointer events into `InputState` (position in device pixels, buttons, wheel), applied in the heartbeat's Input phase.
- [ ] **Fallback**: when `requestContext()` returns null, show a Compose message ("This site uses WebGPU…") and use the CPU `LifeEngine`. Also handle `device.lost`: recreate the device and scenes once, then fall back.

**Done when:** a WebGPU clear color or triangle shows through a working Compose menu, navigation plays configured transitions on both layers in sync, the back button works, clicks reach the right layer, resizing is correct at any DPR, and the fallback works with WebGPU disabled.

## Phase 5 — Game of Life on the GPU  _(M)_

- [ ] State: two `u32` buffers (or `r32uint` textures) swapped every generation ("ping-pong"). Grid size comes from a uniform; offer a bounded and a wrap-around mode.
- [ ] Compute pass: `@workgroup_size(8, 8)`, one thread per cell, reading 8 neighbours. **Rules as uniforms**: a birth bitmask and a survive bitmask, so every Life-like rule works (B3/S23, HighLife B36/S23, Seeds B2/S…), selectable from a Compose dropdown and kept in the URL through the destination's arguments.
- [ ] Render pass: a fragment shader reads the state buffer directly (no per-cell draw calls) and draws grid lines, cell age and colour fading.
- [ ] Editing: while paused, a pointer drag draws cells through `queue.writeBuffer` of a small region (no full upload).
- [ ] Population: `atomicAdd` into a counter buffer in the compute pass, read back through **two rotating `MAP_READ` buffers** a few frames behind (rotated on `Frame.index`), so the GPU never stalls.
- [ ] Speed: generations per second on the `life` clock with `fixedSteps`; play/pause is just that clock's `paused`.
- [ ] **Tests against the reference**: a browser test runs N generations on the GPU for known patterns (glider, R-pentomino, gun), reads the result back, and compares it with `LifeEngine`.
- [ ] Scale goal: 2048×2048 at 60 fps, with zoom and pan.

**What you learn:** compute passes, ping-pong buffers, atomics, reading data back without stalls, testing GPU code against a CPU reference.

## Phase 6 — Boids with compute shaders (flagship)  _(L)_

Built in steps; each step ships on its own. The simulation steps on the `boids` clock.

### 6.1 Naive O(N²) version
- [ ] Particle buffers `{ pos: vec2f, vel: vec2f }`, ping-ponged. The compute pass applies separation, alignment and cohesion within a perception radius. Integration uses a max speed and max force, and edges wrap.
- [ ] Rendering: the vertex shader reads the storage buffer directly (**no vertex buffer**); each boid is a triangle rotated to its velocity, drawn instanced.
- [ ] Start with N = 4,096 and confirm it looks right. Turn the old `Rule`/`Vec2` code into a small CPU reference that checks one simulation step for N = 64.

### 6.2 Spatial grid (so it scales)
Per frame, compute passes over a grid whose cell size equals the perception radius:
1. Clear the per-cell counters.
2. **Count**: `atomicAdd` each boid into its cell.
3. **Prefix sum** (exclusive scan) over the cell counts: a scan inside each workgroup, a pass over the block sums, then an add-back pass (Blelloch-style).
4. **Scatter**: write boids into a buffer sorted by cell (a counting sort).
5. **Neighbour search**: each boid only looks at the 3×3 surrounding cells of the sorted buffer.

- [ ] Goal: **100k+ boids at 60 fps** on a mid-range laptop GPU; try for 1M.
- [ ] Unit test for the scan against a CPU scan on random input (browser test).

### 6.3 Interaction and parameters
- [ ] Compose sliders for the rule weights, perception radius, max speed and boid count; these write a uniform buffer.
- [ ] Pointer: attract with the left button, repel with the right; the wheel sets the radius.
- [ ] Extras: predators (a second species), obstacles (signed distance fields in the shader), trails (render into a texture that fades out), colour by speed or heading.

### 6.4 Profiling HUD
- [ ] If `has("timestamp-query")` (the typed setlike from 1.3/1.4) is true, request the feature and measure every pass. A Compose overlay shows the milliseconds per pass, the boid count and the FPS (from the heartbeat). Seeing where GPU time goes is both a learning tool and a showpiece.

**What you learn:** parallel algorithms (scan, counting sort, spatial hashing), GPU profiling, designing a simulation around memory access.

## Risks to watch

| Risk | Mitigation |
|---|---|
| The Skiko white-clear workaround breaks after a CMP update | Isolated in `AppRoot`, and a test screenshot in the smoke test; watch SKIKO-949 |
| No WebGPU (Firefox on Linux, some GPUs, older Safari) | Typed null path, CPU fallback page, clear message; the navigation graph works the same without the GPU layer |
| GPU device lost (driver reset, tab in background) | `device.lost` watcher recreates the device and scenes once, then falls back |
| A heavy subscriber delays the whole frame (synchronous heartbeat) | Keep per-frame CPU work small (the GPU does the heavy work); the HUD shows time per phase so problems are visible |
| Navigation framework grows too general | Start from the site's real transitions; add combinators only when an edge needs them |
| Uniform layout and alignment bugs | Helpers written against WGSL rules now; the Phase 8 generator later |
| Element-by-element Kotlin↔JS copies | Keep data on the GPU; reuse staging typed arrays; upload only small regions |
| Dictionary `null` vs `undefined` | Factories never set absent keys; a golden test and a runtime test cover it |
| A spec update changes the generated API | The IDL is committed and updated only by hand; golden tests show the change as a diff |

## Suggested order

Phase 0 → **Phase 1 and Phase 2 in parallel** (they're independent: one is build tooling, the other pure Kotlin) → Phase 3 → Phase 5 (simpler compute first) → Phase 6 → Phase 4 → Phase 7. Life comes before Boids because it teaches ping-pong buffers, atomics and readback, all of which Boids needs. The background shader port can happen whenever it's needed as a break from compute work.
